# RC11 corrupted wall edges — pal6 speckle in the BG tile table (2026-08-30)

**Build under test:** `Penta Dragon DX v3.01-924173f3cd82.gbc`
md5 `58e5357354cd2dde8568ab18e4082661`, 524288 bytes.
Tag lineage: `0dd75f9 feat: qualify v3.01 stream rc11`.

**Capture:** `manual_captures/rc11_official_corrupted_wall_edges_2026_08_30.png`
(md5 `d61beae0ef4f349ddabcb5240b0a8c30`)

## Symptom

Dungeon room (stage 1) renders its stepped wall / floor-edge tiles in **two
different slate tones** against the lavender floor, with a hard seam where they
meet. Static — identical across 5 consecutive captured frames, so this is a
fixed wrong-palette assignment, **not** a bg_sweep race or a scroll-edge
flicker.

## Root cause (verified against shipped ROM bytes)

The BG tile-ID → palette table routes a scattered subset of the floor-edge
transition band to **palette 6**, interleaved with palette 0, so adjacent cells
of the same wall material get different palettes.

### 1. Both palettes are provably on screen

Colour histogram of the capture, cross-referenced against
`palettes/penta_palettes_v097.yaml` (BGR555 → RGB):

| Palette | Entry | BGR555 | RGB | px in capture |
|---------|-------|--------|-----|---------------|
| pal 0 "Dungeon" | c1 | `7E94` | `#a4a4ff` | 5371 |
| pal 0 "Dungeon" | c2 | `3D4A` | `#52527b` | 1889 |
| **pal 6** | c1 | `7F1B` | `#dec6ff` | 1268 |
| **pal 6** | c2 | `3D08` | `#42427b` | 1033 |

Two slate tones (`#52527b` from pal0, `#42427b` from pal6) on one material.

### 2. The table in the shipped ROM is speckled

The 256-byte table generated by `build_v301_gdma.BG_TABLE_BYTES` was found
**byte-for-byte** in the shipped ROM:

```
exact 256-byte table found at ROM offset 0x037000
  = bank 13 offset 0x7000
```

So this is definitively the table RC11 ships. The floor-edge transition band:

```
tile:  13 14 15 16 17 18 19 1A 1B 1C 1D 1E 1F 20 21 22 23
pal:    0  6  0  6  6  6  6  6  0  6  0  6  0  0  0  0  0
```

**8 palette flips** across a band that should be uniform. The same speckling
recurs at `0x34-0x38`, `0x41-0x49`, `0x54-0x59`. Overall 36 of 256 tile IDs
route to pal6.

Full palette histogram over the 256 tile IDs:

```
{0: 123, 1: 5, 2: 16, 3: 8, 4: 24, 5: 32, 6: 36, 7: 12}
```

### 3. This is a known, previously-fixed regression

`CLAUDE.md` pitfall #4 documents this exact range:

> **The "purple specks on floor" bug** (v297 calibrated-table attempt):
> tile IDs 0x13-0x23 are FLOOR-EDGE TRANSITION tiles, not walls. Routing them
> to pal6 (slate) created visible seams on the floor.
> Fix: route 0x13-0x23 to pal0; OR (v299 minimal) only colorize items +
> hazards, everything else stays pal0.

A calibrated-table variant appears to have been reintroduced without
re-applying that fix.

## Suggested fix

Route `0x13-0x23` to pal0 in `BG_TABLE_BYTES` (`scripts/build_v301_gdma.py`),
per the v297 resolution. The other speckled bands (`0x34-0x38`, `0x41-0x49`,
`0x54-0x59`) should be reviewed the same way — verify each ID is genuinely a
wall face before giving it pal6, since edge/transition tiles in those runs will
produce the same seam.

## Open / unverified

- **Which tile IDs the specific wall cells in this room use was NOT confirmed.**
  The root cause above is inferred from the palette-colour match plus the table
  contents. A save state from this room would let the tilemap be read directly
  and the offending IDs named exactly rather than by range. Worth doing before
  committing a fix.
- No check was made for whether any *arena* table (`_bg_table_shalamar` etc.)
  has the same speckle — only the base dungeon table was examined.
